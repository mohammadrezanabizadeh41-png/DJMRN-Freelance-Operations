## 2. Technical facts that should materially shape the preview (NOT a vendor-engine copy)

**A. Camera path is data, not the flower geometry.**
- Browser-served `/valley/camera-path07.glb`: 10,132 bytes, glTF 2.0, **one perspective camera, zero meshes, zero materials**, 200 sampled timestamps on each of translation/rotation/scale tracks from 0 to about 8.291667 seconds, linear samplers; perspective `yfov≈0.399596 rad`, z-near 0.1, z-far 1000. These are source animation sampler facts, NOT proven site runtime loop/easing/camera speed. **Author a distinct original spline** with camera motion proportional to interaction and performance.
- Do NOT mistakenly treat this GLB as a textured 3D valley or mesh geometry asset.

**B. Flowers rendered as an unusually large GPU point workload, with image/sprite inputs.**
- In the historical live Vega 8 / Chromium WebGL2 draw audit: once per sampled frame `drawElements(GL_POINTS, 960000)`, once `drawElements(GL_TRIANGLES, 6)`, and 14 `drawArrays(GL_TRIANGLES, 3)` = **16 draw calls/frame**; NOT 960,000 unique flowers or a recommended local budget.
- 11 linked WebGL programs seen at boot. The primary flower/leaf program exposes 36 active uniform entries and 12 active vertex attributes. Strong hint names include `uDispersalProgress`, `uDispersalAmountMultiplier`, `uMousePosition`, `uSpriteSheetPool`, `uSpriteSheetPool2`, `uSpriteSheetMix`, `uFlowerBloomDistance`, `uLeafGrowDistance`, `uTerrainOffsetY`, `uNegativeSpaceDeepness`, `uCamFov` and `uTime`; relevant attributes include `aSpriteScale`, `aRandomSeed`, `aPoolId`, `aValleySide`, `aSpriteIndex`, `aFlowerGrowNoise`. These are observed runtime parameter names, NOT verified equations. Define entirely original parameter names/implementation if appropriate.
- Site-observed resource types include `pool_summer.png`, `pool_winter.png`, `terrain.png`, `vignette.png`, `dust-particle.png`, `rays/ray1,ray2,ray3.png` and optional `audio/ge-ambient.mp3`. Their roles are inferred from names/network/JS references; create **original art/sprites** and no soundtrack by default.

**C. Observed user-visible motion:**
- Dark central corridor with pink/purple/yellow luminous organic flower banks and strong layered depth; moving pointer left/right changes apparent clustering/view; mouse wheel changes camera-like rendered view without traditional page scrolling; hover on the primary CTA **visibly disperses/dims flowers to floating luminous points** and exit restores dense flowers. Click/hold/drag-to-accelerate is a **DJMRN requested experiment**, NOT causally confirmed original Gladeye behavior. Touch hardware and actual original reduced-motion fallback remain unverified.

**D. Main interaction contract for an original DJMRN demo:**
- `idle`: soft breathing/float and slow camera drift, dark safe central negative-space for future UI.
- `pointermove`: mild bounded camera tilt and point/sprite repulsion/illumination, no huge sudden movement.
- `wheel`: gentle travel through an independently created spline when canvas interaction owns it; never hijack normal page/service scrolling.
- `focus / hover a demo trigger`: visible, smooth flower dispersion and soft bloom/dimming. `focus-exit / restore`: reversible gradual regrowth/reconvergence.
- `pointerdown / drag / release`: optional new DJMRN experiment with clear visual feedback; mark as original behavior.
- `touch/mobile`: responsive rendering and obvious touch-safe test controls, keep vertical page movement functional.
- `reduced motion / WebGL lost / unavailable`: functioning reduced-motion 2.5D/Canvas fallback (not black screen); no unsafe GPU busy loops; focus/text controls remain usable.
- `audio`: off by default, preferably omit entirely from this prototype.

**E. Runtime/quality and performance constraints:**
- User laptop Lenovo 81W1 Ryzen 5 3500U / Radeon Vega 8, 8GB physical but approximately 5.88GiB usable by Windows. This device cannot comfortably run Docker + many render tools simultaneously; prototype must be a lightweight browser scene. Historical short JS animation intervals around 16.7ms median and 33.4ms p95 do not prove GPU frame time.
- Trial particle count should be **measured, not copied**: begin with ~12k–25k points desktop and ~3k–8k touch, adjust based on browser frame timings; use adaptive quality and pause when hidden. One renderer, no duplicated Three + Babylon stacks. Prefer original procedural sprites or tiny licensed assets. CSS/Canvas 2.5D alone may be enough for a fallback; real WebGL2/Three.js is appropriate if needed for the requested camera-depth scene.
- Evidence X10: official Browsertrix 1.15.4 full image pulled, original bounded capture WACZ 10.76MB / 53 CDX records (49 HTTP 200, 1 HTTP 204, 3 synthetic/non-status), including **one GLB that exactly matches the previously observed X01 camera path**, 8 original PNG plus one generated screenshot, MP3 and client JS. 44 CDX records have digests matching X01 content.
