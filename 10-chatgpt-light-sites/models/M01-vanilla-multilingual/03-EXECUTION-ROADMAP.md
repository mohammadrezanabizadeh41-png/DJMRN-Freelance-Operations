## قرارداد سراسری واکنش‌گرایی — موبایل، تبلت، لپ‌تاپ و دسکتاپ
این **الزام افقی تمام S02–S20** است، نه یک پروژه جدید یا افزونه‌ای که فقط در پایان بررسی شود. **یک HTML/DOM معنایی برای هر صفحه/زبان** با CSS fluid و حداقل breakpointهای مبتنی بر محتوا؛ mobile-first، `<meta name="viewport" content="width=device-width, initial-scale=1">`، Grid/Flexbox و در صورت نیاز Container Queries. هیچ وابستگی Vite/React/WordPress اضافه نمی‌شود.

| کلاس نمایش (هدف UX) | نمونه عرض تست CSS px | رفتار طراحی مورد انتظار | ورودی‌ها |
|---|---|---|---|
| موبایل (باریک و عریض) | **320، 360، 390، 430** | یک ستون اصلی، دکمه/ناوبری قابل لمس، فرم و cart بدون overflow؛ منوی موبایل قابل استفاده | touch و keyboard/assistive |
| تبلت portrait/landscape | **600، 768، 820، 1024** | ۱–۲ یا ۳ ستون برحسب محتوا، navigation و کارت‌ها مناسب لمس؛ چرخش بدون گم‌شدن state | touch، قلم، keyboard اختیاری |
| لپ‌تاپ و دسکتاپ | **1024، 1280، 1440** | navigation کامل متناسب عرض، layout چندستونی با سقف عرض خواندن؛ hover به‌عنوان enhancement نه تنها راه تعامل | mouse، keyboard، touch hybrid |
| صفحه عریض (تکمیلی، نه خانواده مستقل) | **1920** | محتوا با `max-width` خوانا بماند، فضا به حاشیه/تصویر مناسب اختصاص یابد، اجزا بی‌دلیل کشیده نشوند | mouse/keyboard |

*این اعداد **نقاط نمونه‌برداری برای آزمون** هستند، نه breakpoints اجباری یا تضمین رفتار مدل خاص گوشی/تبلت. breakpoint واقعی از جایی که محتوا می‌شکند در S06 تعیین می‌شود؛ می‌تواند در `rem` و با `clamp()`، `minmax()` و `auto-fit` پیاده شود. تبلت افقی و لپ‌تاپ کوچک ممکن است عرض یکسان داشته باشند؛ سایت به **viewport و قابلیت ورودی** واکنش نشان می‌دهد نه user agent.*

**خروجی هر مرحله از S08:** در نمونه HTML واقعی، حداقل snapshot/تست عرض 390 (موبایل)، 820 (تبلت)، 1366/1440 (لپ‌تاپ/دسکتاپ). در S18 ماتریس کامل اجرا شود؛ RTL فارسی/عربی، LTR انگلیسی/ترکی/آلمانی با طول رشته متفاوت، portrait/landscape، zoom، صفحه‌کلید و touch تست شوند. ساختار و محتوای سایت برای هر دستگاه واحد می‌ماند.

**معیار توقف:** هر horizontal overflow ناخواسته، محتوای حذف‌شده، دکمه غیرقابل‌دسترس، شکست language switcher، سبد خرید unusable، اجزای فقط-hover یا ترتیب خواندن نادرست در هر کلاس نمایش = مرحله FAIL. موارد carousel/tables که ماهیتاً نیازمند اسکرول افقی هستند باید فقط درون container مشخص، accessible و با کنترل دیده‌شونده باشند.

**مبنای منابع:** [MDN Responsive Design](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design) · [web.dev Breakpoints](https://web.dev/learn/design/media-queries) · [W3C WCAG 2.2 Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). جزئیات فنی در [04-I18N-SEO-COMMERCE-SECURITY.md](04-I18N-SEO-COMMERCE-SECURITY.md) و تست‌ها در [05-QA-AND-HANDOFF.md](05-QA-AND-HANDOFF.md).

## اصلاح سیاست RAM و ابزارسازی حرفه‌ای — 2026-11-22 (دستور جدید مالک)

**تصمیم برتر بر محدودیت‌های قبلی:** حدود **۲GiB RAM آزاد** هدف *پیش از آغاز* کار حرفه‌ای/تست سنگین است، **نه سقف نرم‌افزارها، نه حداقلِ لازم در تمام مدت اجرا و نه دلیل حذف GIMP/Blender/Penpot/چندابزاری**. ممیزی WMI: دو ماژول ۴GiB نصب‌شده، ویندوز حدود ۶۰۲۰MiB قابل استفاده، در لحظهٔ جدید **۱۶۶۴MiB** آزاد (فاصله ۳۸۴MiB تا هدف). بار دیگر **۱۶۱۳MiB** ثبت شد؛ همه لحظه‌ای‌اند. Pagefile تخصیص‌یافته حدود ۸۶۴۴MiB است و جایگزین سرعت RAM نمی‌شود. GIMP 3.2.8 و Blender 5.3.0 با اجرای فرمان نسخه تأیید شدند، **رندر/طراحی سنگین آنها هنوز آزمایش نشده است**.

**منطق استفاده:** حرفه‌ای‌ترین نتیجهٔ متناسب با ماهیت سایت را انتخاب کن؛ ابزار طراحی/رندر/پردازش تصویر می‌تواند در کنار کد HTML/CSS/JS و ابزار QA استفاده شود و **نیازی نیست سایت هنگام انتشار به همان نرم‌افزار وابسته باشد**. برای S06/S10 بازسازی، S11 نمونه‌کارها، S12 تصاویر بسته‌ها و S14A داشبورد، مسیر **طرح قابل‌ویرایش → ساخت رسانهٔ اصیل GIMP/Blender → خروجی وب بهینه → اجرای Node → پیش‌نمایش Chrome/Edge → Playwright/axe/Lighthouse** باید به‌عنوان گزینهٔ حرفه‌ای سنجیده شود؛ بدون الزام اینکه همهٔ برنامه‌ها در همهٔ کارها استفاده شوند. **ترکیب هم‌زمان** در صورت ارزش واقعی و اندازه‌گیری موفق مجاز است؛ موازی‌بودن هدف مستقل نیست.

**کنترل منابع مرحله‌ای:** رسیدن به حدود ۲GiB RAM آزاد با بررسی/بستن برگشت‌پذیر ابزارهای غیرضروریِ موردتأیید مالک و حفظ VPN/Bridge/کار ذخیره‌نشده. زمان اجرا RAM Available، memory commit/pagefile، GPU/CPU، زمان/پایداری و نتیجهٔ بصری ثبت شود. اگر افت پاسخ‌گویی یا paging شدید دیدی، اول preview/texture/render sample/worker/تعداد tab را تدریجی کم کن یا ترتیب render→preview→test را تغییر بده؛ **خروجی حرفه‌ای یا پوشش آزمون را حذف نکن**. هیچ Stop-Process عمومی، تغییر دائمی ویندوز، نصب/پرداخت/اتصال حساس بدون مجوز.

- **PROPOSAL:** frontend پنج‌زبانهٔ HTML/CSS/vanilla JS و دارایی‌های سبک را **reuse** کن؛ سرویس عملیاتی را در همان مخزن اما با boundary جدا و یک **modular monolith** با API سمت سرور، پایگاه دادهٔ transactional، identity/session، message dispatcher و payment adapter بساز. ### 2) Domain Contract — purpose / I/O / authority / authorization / failure
| Domain (مالک) | ورودی → خروجی واقعی | منبع حقیقت / مرز دسترسی | خطا و تست پذیرش |
|---|---|---|---|
| Identity | email + phone + proof + credentials → verified active customer | backend + DB؛ email/phone فقط برای هدف مصوب؛ admin فقط دعوتِ دارای مجوز | OTP wrong/expired/resend/duplicate، account enumeration، rate-limit |
| Sessions & authorization | authenticated principal + role → permitted operation | session server/verified cookie؛ deny-by-default؛ server enforces per-resource ownership | stolen/expired/rotated session، CSRF، user→admin bypass، IDOR/BOLA |
| Membership | internal immutable `customer_id` → public opaque `membership_code` | DB unique constraint؛ public code **not secret/not login** | collision/retry، changed email/phone، parallel signups، account disabled |
| Catalog & price | approved item/price/availability → server price snapshot | DB/approved catalog revision؛ client totals never authority | price tamper, out-of-stock, stale catalog, duplicate SKU |
| Cart & order | authenticated customer + validated items → durable order with owner_id | DB transactional `orders`/`order_items`؛ RLS/authorization each read/write | replay/reload, concurrent carts, forged owner_id, idempotency |
| Payment | pending order → PSP session → signed event → paid/failed/refund | PSP is transaction result authority, DB projection keeps event IDs | callback forged/duplicate/out-of-order/timeout, refund reconciliation |
| Fulfillment & notifications | paid order → entitled delivery + email/SMS status | DB event/outbox, retry with idempotency; approved notifications only | retries/restart, delivery failure, duplicate entitlement |
| Administration | invited staff + MFA + scoped role → audited catalog/order/customer actions | server privilege checks; append audit event on sensitive writes | privilege escalation, bulk export, lost MFA, rogue admin |
| Content Studio (existing S14A) | local draft JSON → preview/validated export | GitHub content source via local protected tooling, **not account/order DB** | editor LAN exposure, invalid draft, rollback |
| Privacy/Operations | explicit consent/policy, retention, support → secure rights handling | selected DB & runtime logs; minimum PII; protected backup | deletion/restore, incident, notification failure, unbounded logs |

### 3) قرارداد داده و ماشین حالت — طراحی پیشنهادی، هنوز Schema/Migration نیست
- `principals(id UUID/ULID immutable, status, created_at)`؛ identity معتبر فقط پس از authentication. `customer_profiles(principal_id UNIQUE, membership_code UNIQUE opaque nonsequential, locale, status)`؛ public membership code برای پیگیری و UI است، **هیچ endpoint فقط با آن مالکیت را نمی‌پذیرد**. `customer_contacts(principal_id, normalized email, E.164 phone, verified_at, changed_at)` با constraint/uniqueness معنادار و امکان تغییر تأییدشده؛ retention طبق قانون/سیاست قابل تعیین.
- `verification_challenges(id, subject, channel, purpose, expires_at, attempts, resend_cooldown, consumed_at)` با کد/توکن مولد تصادفی امن، یک‌بارمصرف، hashed/server-side، expiry کوتاه، throttling در account/phone/IP. **email confirmation = اثبات دسترسی به نشانی، نه second-factor login**؛ برای admin MFA ترجیحاً passkey/WebAuthn یا TOTP، با recovery ایمن و غیرقابل دورزدن با SMS. پیامک ممکن است charge یا محدودیت منطقه‌ای داشته باشد؛ تا cost/eligibility تأیید نشود mock connector تنها گزینهٔ آزمایش است.
- `credentials/session` تحت مدیریت identity provider/سرور انتخابی، نه در JSON public؛ password در صورت انتخاب Argon2id/secure equivalent، session در cookie دارای `Secure`, `HttpOnly`, `SameSite`، rotation/revocation، inactivity/absolute expiry و CSRF defenses؛ audit به session/role/subject متصل ولی هرگز password/OTP/token را log نمی‌کند.
- `staff_memberships(principal_id, role, approved_by, mfa_policy)` فقط با provisioning صاحب‌اختیار ایجاد می‌شود، admin self-register و client-settable role ممنوع؛ `audit_events(actor, action, subject_type, subject_id, outcome, trace_id, time)` append-only قابل نظارت.
- `catalog_products(id, status, price_minor, currency, version)`، `orders(id, owner_principal_id FK, membership_code_snapshot, status, total_minor, currency, created_at)`، `order_items(order_id FK, product_id FK, unit_price_minor_snapshot, qty, total_minor)`، `payment_attempts(order_id, provider_reference UNIQUE, status)`، `provider_events(provider,event_id UNIQUE, verified_at)`، `fulfillments(order_id, grant_id, state)` و `outbox`؛ مبلغ از catalog سمت سرور snapshot می‌شود. `DEMO_CREDIT` هرگز در order/payment واقعی با مبلغ پولی جمع نمی‌شود؛ migration از DEMO به فروش واقعی بی‌تأیید ممنوع.
- **Membership states:** `PENDING_EMAIL → PENDING_PHONE → ACTIVE → [SUSPENDED|CLOSED]`، با `EXPIRED/RESEND` در challengeهای مستقل. ایجاد شناسهٔ عضویت پس از اثبات هر دو کانال و commit اتمیک با DB unique index؛ retry با همان idempotency key دوباره شناسه نمی‌سازد. حالت recovery/change-address باید proof/notification و re-verification داشته باشد؛ SMS delivery failure کاربر را در pending نگه می‌دارد، نه ACTIVE.
- **Order states:** `DRAFT → AWAITING_PAYMENT → PAID → FULFILLING → FULFILLED` یا `FAILED/CANCELLED/REFUND_PENDING/REFUNDED` تحت transition guards. موفق‌شدن redirect مرورگر سند پرداخت نیست؛ تنها callback با امضای معتبر و استعلام قابل اعتماد provider اجازهٔ تغییر وضعیت به PAID می‌دهد. ثبت سفارش با transaction و idempotent event processing و کلید order داخلی، نه ایمیل، موبایل یا membership_code ورودی مشتری.
- **Visibility:** `customer` فقط حساب/سفارش خود؛ `support` صرفاً مشاهدهٔ مجاز و ماسک PII؛ `catalog_editor` فقط محتوا؛ `order_operator` فقط سفارش‌های مجاز؛ `admin` با MFA برای مدیریت نقش‌ها؛ `owner/superadmin` برای تغییر دسترسی سطح بالا با step-up و ثبت audit. permissions در **هر** API و query اعمال می‌شود؛ UI به‌تنهایی role enforcement محسوب نمی‌شود.

### 7) الزامات ویژهٔ UX برای هر دو درگاه ورود
- **Visitor:** `/{locale}/account/register`, `/verify-email`, `/verify-phone`, `/login`, `/recover`, `/me`, `/me/orders/:id`, `/me/security` در نسخهٔ تولیدی؛ همهٔ routes دارای login-gated/noindex، فرم واضح، مرحله‌بندی ۱/۲، امکان paste/autocomplete OTP و password managers، پیام‌های بدون account enumeration، حافظهٔ امن و متن resend/expiry به پنج زبان. پیام تأیید عضویت **تنها پس از verify کامل و transaction commit** کد عضویت را نشان می‌دهد؛ در صف ارسال ایمیل/پیامک قطعی ارسال‌شده ادعا نمی‌شود.

- **خطاها:** اشتباه بودن OTP، تاخیر/قطع SMS، تغییر شماره، ایمیل تکراری، نشست منقضی، دو تب همزمان، browser back/refresh، انصراف از پرداخت، تکرار webhook و استرداد مالی با UI پنج‌زبانه و تست‌های منفی پوشش داده شوند. Accessibility از ابتدا (WCAG 2.2 Accessible Authentication 3.3.8) شامل اجازهٔ paste، autofill، نمایش خطای قابل فهم و alternative method است.

## الحاق زیرساخت جامع نسخهٔ واقعی — 2026-11-22 (Infrastructure Readiness / RESEARCHED, NOT PROVISIONED)

**منبع واحد وضعیت:** همین نقشهٔ راه. این الحاق از درخواست مالک برای شناسایی **تمام** dependencyهای سایت واقعی نشئت گرفته و زیرمجموعهٔ همان M01 است؛ مربوط به `09-self-marketing-website` یا مدل‌های دیگر نیست. **S01–S12 فقط DEMO PASS**، **S12A و P00–P18 و گیت‌های زیر همگی باز**. شناسایی ارائه‌دهنده و داشتن MCP معادل provisioning/production نیست. تا تأیید هزینه/صلاحیت/مجوز، هیچ اتصال جدید، حساب، دامنه، DB، SMS، ایمیل، درگاه، رمز، schema، انتشار یا سرویس تولیدی ایجاد نمی‌شود.

### IA. زنجیرهٔ زیرساخت موردنیاز و وابستگی واقعی

```text
Owner/merchant/jurisdiction & consent decision (I00)
     ├─ free development: GitHub source + Node local + SQLite fixture + mock SMTP/SMS/PSP
     └─ deploy gate: account/region eligibility → DNS/domain/subdomain (I01)
              → static asset/CDN hosting (I02) + HTTPS edge AND origin (I03)
              → runtime API/secret/CI (I04,I05,I06) → durable SQL+backup (I07,I08)
              → email sender DNS SPF/DKIM/DMARC (I09) + approved OTP/SMS (I10)
              → identity/session/passkey/MFA (I11) → staff roles (I12)
              → order/price provider + approved signed PSP (I13) → fulfillment (I14)
              → private media/files (I15) + durable outbox/retry/scheduler (I16)
              → WAF/rate-limit/abuse (I17) + logs/monitor/alerts (I18)
              → policies, retention/consent/legal (I19) + staging/test/rollback (I20)
     ALL I-gates and T31–T45 → P17 verification → P18 owner-controlled launch.
```

**Stack minimum:** front-end فعلی را حفظ کن، **یک runtime API** (در صورت نیاز Worker یا یک Node service)، **یک DB اصلی** (نه Supabase+Neon همزمان)، **یک identity authority**، یک کانالِ تأییدنشدهٔ mock قبل از اتصال SMS واقعی، یک sender ایمیل و یک PSP تأییدشده. CDN/DNS/TLS و WAF اگر در host ادغام باشند تکرار نکن. Queue، object storage و cache در صورت نیاز کاربردی در همان سرویس مشترک یا کد deterministic پیاده‌سازی شوند، نه چند زیرساخت مستقل. وجود gap مجوز خرید یا ثبت‌نام نیست.

### IB. گیت‌های چک‌پذیر زیرساخت — هرکدام مستقل، NONE IMPLEMENTED

- [ ] **I00 — حوزهٔ قضایی/صلاحیت/بودجه:** کشور اقامت قانونی مالک/حوزهٔ ارائهٔ خدمات، نوع محصول، سن/حریم خصوصی/پرداخت و مخاطب SMS مشخص شود. قرارداد ToS/KYC/merchant eligibility با اسناد رسمی هر provider، عدم دورزدن هویت و سقف هزینهٔ صفر یا approved cap. **STOP** اگر منطقه/قیمت/overage = UNKNOWN.
- [ ] **I01 — دامنه و DNS:** ابتدا subdomain آزمایشی `*.pages.dev` یا `*.workers.dev` در صورت قابلیت قانونی و بدون هزینه؛ دامنهٔ سفارشی همیشه خرید/تمدید احتمالی دارد. DNS zone، A/AAAA/CNAME، ownership verification و DNSSEC با آزمون resolve و rollback؛ هیچ دامنهٔ پولی بدون approval.
- [ ] **I02 — میزبانی HTML/CSS/JS/CDN:** publish staging همان بیست route نمونه، ۵ زبان، cache policy، invalidation/preview و noindex، build quotas و commercial policy؛ بدون بازنویسی فریم‌ورک. تست HTTP 200، no-JS و بازگشت نسخه.
- [ ] **I03 — HTTPS/TLS end-to-end:** معتبر بودن hostname/certificate و renewal، redirect HTTP→HTTPS، HSTS فقط بعد از اثبات، TLS از مرورگر تا edge **و** از edge تا origin در صورت وجود، تنظیم Full(strict)/equivalent. `Secure` cookies، passkey secure origin، CORS/CSRF را جداگانه تست کن؛ TLS رایگان به معنای دامنهٔ رایگان نیست.
- [ ] **I04 — runtime API و شبکه:** یک isolated serverless Worker/Function یا Node web process برای register/verify/login/order/admin callbacks؛ timeout/sleep/startup، request/body limits، firewall، health endpoint، resource budget و API contract؛ **Render Free sleep** برای تراکنش حساس قبل از حل durability/availability مناسب فرض نشود.
- [ ] **I05 — کلیدها/اسرار/سرویس‌اکانت:** provider keys، JWT/session keys، webhook signing keys، DB connection، runtime env secrets و rotation با least privilege؛ هیچ secret داخل Git/HTML/ChatGPT/CI logs؛ IAM reviews، audit و روش revocation.

- [ ] **I08 — backup/restore/retention:** backup encrypted مستقل از DB provider، زمان‌بندی و offsite access، restore rehearsal، recovery point/time objectives، retention/immutable copy در صورت الزام؛ Free-plan backup را از provider حدس نزن.
- [ ] **I09 — تأیید و ایمیل transactional:** sender domain، SPF/DKIM/DMARC، email-verify link single-use، receipt/support/recovery templates پنج‌زبانه، bounce/suppression، daily/monthly quotas و error queues؛ approved SMTP/API + deliverability proof.

### IH. تکمیل راه‌حل HTTPS بدون خرید SSL یا هاست تکراری
- **[Let’s Encrypt](https://letsencrypt.org/about/)**: گواهی TLS رایگان، خودکار و عمومی (CA)؛ اگر یک VPS/origin واقعی و دامنهٔ قابل اعتبارسنجی داریم گزینهٔ I03 است، **نه** سرویس میزبانی/API/دامنه. با [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https) می‌توان certificate provisioning/renewal و redirect را با منبع‌باز مدیریت کرد؛ monitoring renewal و تست host/origin لازم است. نصب Caddy در این turn انجام نشده.
- **[Render-managed TLS](https://render.com/docs/tls)** و **[GitHub Pages HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)** نیز certificate رایگان/managed ارائه می‌دهند؛ GitHub Pages فقط برای static demo/presentation، نه runtime accounts/payment، مناسب است. اگر Cloudflare Pages یا Render خود TLS و CDN را پوشش دادند، SSL provider/VM/proxy اضافی نساز.
- **[Cloudflare Full(strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)** برای معماری دارای proxy و origin جدا؛ صرف روشن‌کردن Universal SSL در edge برای احراز هویت end-to-end کافی نیست. HSTS و DNSSEC بعد از validation و rollback نه با تنظیم بدون آزمون.
